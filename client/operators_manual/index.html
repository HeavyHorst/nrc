1. INTRODUCTION

1.1 SYSTEM OVERVIEW

nrc is a WebSocket collaboration server with ephemeral chat and persistent tasks, notes and files. Operators can enable bounded room-message retention.

The NRC-300 terminal interface provides operators with complete visibility into system state: live metrics, thread allocation, connection counts, and message flow. This manual describes operation, configuration, and troubleshooting of the complete system.

1.2 KEY SPECIFICATIONS

LATENCY: <100ms round-trip
CONCURRENCY: 65K connections per thread
MEMORY MODEL: Thread-per-core sharding
PROTOCOL: Binary custom frame
ARCHITECTURE: Non-blocking I/O, io_uring
LANGUAGE: Odin (dev-2025-09)

1.3 HARDWARE REQUIREMENTS

MINIMUM: 2-core CPU, 256MB RAM, Linux kernel 5.1+

RECOMMENDED: 8+ core CPU, 2GB+ RAM, Linux kernel 6.0+

NETWORK: Gigabit Ethernet or equivalent, stable sub-100ms RTT

2.2 THREAD MODEL

NRC uses a thread-per-core architecture with explicit per-thread queuing:

  • Main Thread (Acceptor): Accepts incoming TCP connections, enqueues pending connections to worker thread channels
  • Worker Threads (N = CPU count): Each processes connections from its dedicated queue, handles I/O events via io_uring
  • Workspace Isolation: Each thread maintains per-workspace state (conversations, subscriptions, nicknames, tasks, agendas)
  • Conversation Routing: Conversations are identified by 64-bit ID; hash(conversation_id) % thread_count determines assignment
  • Thread-Local State: Buffers, message sequence counters, byte pools, WAL logs - no atomic operations in hot path
  • io_uring Per-Thread: Each worker has its own io_uring ring for efficient kernel I/O batching
  • No Global Locks: Connections never migrate between threads; subscriptions/messaging handled locally within assigned thread

2.3 MEMORY LAYOUT

THREAD STACK: 2MB default per worker thread
TLS BUFFERS: 8KB receive buffers per connection (provided by kernel io_uring)
BYTE POOL (per thread): Thread-local send buffer pool, reusable allocations
PENDING QUEUE CAPACITY: 16384 pending connections per thread channel
CONNECTIONS PER THREAD: 65535 maximum (file descriptor limit)
WORKSPACE STATE: Per-thread map of workspace ID → conversations/subscriptions/tasks
WAL LOG: Task WAL + Agenda WAL per thread (ULID-named append-only files)

3.8 CONVERSATION ROUTING

Conversations are identified by 64-bit unsigned integers. The server routes messages using a hash function to assign conversations to worker threads:

    thread_id = hash(conversation_id) % thread_count

This ensures all messages for a conversation are processed by the same thread, eliminating inter-thread synchronization overhead for conversation state. No distributed locks needed.

3.9 PARSING STRATEGY

Protocol parsing is designed for zero-allocation performance:

  • Fixed-size headers with known offset calculations
  • Length-prefixed variable data (u16 or u32)
  • Direct byte slice access to content (no copying)
  • Thread-local stack buffers for collection parsing
  • Big-endian for network portability

4. PERSISTENCE LAYER

4.1 OVERVIEW

NRC implements a Write-Ahead Log (WAL) strategy for durable storage of tasks and agendas. Unlike traditional systems with global log files, NRC uses per-thread WAL with no distributed consensus overhead. Each worker thread maintains its own append-only log files, ensuring data durability without inter-thread coordination.

Design Principle: Tasks and agendas persist to disk before acknowledgment; ephemeral messages (conversations) do not. This guarantees that structured work state survives server restarts while preserving the real-time, ephemeral nature of chat.

4.2 PER-THREAD WAL MODEL

Each worker thread owns its WAL files:

    Thread 0 → data/tasks_thread_0.log
           → data/agenda_thread_0.log
    Thread 1 → data/tasks_thread_1.log
           → data/agenda_thread_1.log
    Thread N → data/tasks_thread_N.log
           → data/agenda_thread_N.log

No cross-thread coordination. Task routing via hash(conversation_id) % thread_count guarantees that a conversation's tasks always go to the same thread, so each thread writes only its own data. Recovery on startup replays each thread's logs independently.

4.3 RECORD FORMAT

All WAL records use a uniform 48-byte header followed by variable-length payload:

    ┌──────────────────────────────────────────────────────┐
    │ RECORD HEADER (48 bytes)                             │
    ├──────────────────────────────────────────────────────┤
    │ Offset  Size  Field        Description               │
    │ ------  ----  -----------  ----------------------    │
    │ 0       4     magic        Entity magic (0x4E524354)  │
    │ 4       2     version      Format version (1)         │
    │ 6       1     op           Operation (1=Create,etc)   │
    │ 7       1     flags        Reserved                   │
    │ 8       4     length       Payload size (bytes)       │
    │ 12      32    prev_hash    SHA-256 chain hash        │
    │ 44      4     record_hash  XXH32 CRC checksum        │
    ├──────────────────────────────────────────────────────┤
    │ PAYLOAD (variable, length bytes)                     │
    │ ┌──────────────────────────────────────────────────┐ │
    │ │ 2     ws_len     Workspace ID string length      │ │
    │ │ var   workspace  Workspace ID string             │ │
    │ │ var   entity     Entity-specific data            │ │
    │ └──────────────────────────────────────────────────┘ │
    └──────────────────────────────────────────────────────┘

4.4 HASH CHAIN (TAMPER EVIDENCE)

Each record chains to the previous via SHA-256 hash. The prev_hash field contains the SHA-256 hash of the previous record (header + payload). If any earlier record is corrupted or modified, the chain breaks and replay detects tampering:

    Record 1: SHA256(header₁ + payload₁) → hash₁
    Record 2: prev_hash = hash₁, SHA256(header₂ + payload₂) → hash₂
    Record 3: prev_hash = hash₂, SHA256(header₃ + payload₃) → hash₃
    ...
    On replay: Verify each prev_hash matches previous record's hash

If verification fails at any point, replay stops and truncates the log at the last valid record. This prevents loading corrupted or maliciously modified state.

4.5 TASK PERSISTENCE

Task operations use tagged-field format for forward/backward compatibility:

Operation Description
Create (op=1) New task with full state (title, status, assignee, dates, etc.)
Update (op=2) Task state changed (complete snapshot, not delta)
Move (op=3) Task reordered (complete snapshot)
Delete (op=4) Task removed (tombstone: workspace_id, conv_id, task_id)

Critical Invariant: Every non-Delete record contains the COMPLETE entity state. Create, Update, and Move all serialize all 16 task fields (title, description, status, priority, timestamps, assignee, etc.). This is essential for compaction correctness—when the log is compacted, only the last record per task survives, so it must be self-contained.

4.6 AGENDA PERSISTENCE

Agendas are simpler: a conversation has a single mutable agenda string.

Operation Description
Set (op=1) Agenda content (max 65535 bytes)

4.7 WRITE PATH & BATCHING

Write operations are batched for performance:

  1. Thread-local buffer accumulates records (up to 128KB)
  2. When batch fills, single write() syscall flushes all pending records
  3. After write completes, check fsync thresholds
  4. fsync triggered if: (a) 100MB+ pending bytes, OR (b) 1+ second since last fsync
  5. Shutdown performs final flush and fsync

This batching reduces system calls while maintaining sub-second durability guarantees.

4.8 FSYNC STRATEGY & DURABILITY

Byte Threshold 100MB of pending unfsynced data
Time Threshold 1 second since last fsync
Shutdown Flush batch, then force fsync before exit

fsync is called via posix.fsync(), ensuring kernel writeback to persistent storage. Latency is tracked; fsync operations never block the hot path (writes occur in batches before fsync check).

4.9 RECOVERY ON STARTUP

  1. Each thread's worker_thread() calls init_task_persistence() and init_asset_persistence()
  2. If WAL file exists, replay_wal() scans it via mmap (zero-copy)
  3. For each record: verify magic, validate hash chain, check CRC
  4. Apply each valid operation to in-memory state (tasks map, agenda strings)
  5. If corruption detected (broken chain, CRC mismatch): truncate log at last valid record and stop
  6. WAL state (last_hash, record_count) is restored from replay result
  7. If no log file exists, thread starts with empty state (creates new file on first write)

Recovery is single-threaded per thread (no cross-thread coordination). Total startup time scales linearly with total log size, typically <1 second for logs <1GB.

4.10 LOG COMPACTION

Logs grow unbounded with repeated updates. Compaction removes outdated records via a two-pass algorithm:

Pass 1: Build Key Map (mmap scan)

    Scan entire log sequentially. For each record:
    - Extract entity key (workspace_id, conv_id, task_id for tasks)
    - Store (offset, record_size, is_tombstone) in map
    - Later records overwrite earlier ones
    
    Result: key_map contains only LATEST state per entity

Pass 2: Write Survivors (fresh hash chain)

    For each entry in key_map:
    - If Delete (tombstone), skip entirely
    - Otherwise, read from source, validate CRC
    - Rewrite to temp .compact file with FRESH hash chain
     (prev_hash and record_hash recomputed for chain continuity)
    - On CRC error: skip record, continue with rest

Finalize (atomic swap)

    - fsync temp file
    - atomically rename .compact over original log
    - reopen WAL handle
    - update WAL state (last_hash, record_count)
Trigger Hourly check; compact if log > 500MB
Blocking Yes - compaction pauses writes (typically <1 sec for 500MB)
CRC Validation Yes - catches corruption during compaction
Hash Chain Validation No - already validated by replay_wal() on startup
On CRC Error Record skipped, compaction continues (maximizes recovery)

Tombstone Handling: Delete operations are marked as tombstones in the key map. During Pass 2, tombstoned keys are excluded entirely from compacted output. This is safe because the key map stores only the FINAL state per key.

    Example sequences:
    Create(K) → Update(K) → Delete(K)           → K excluded
    Create(K) → Delete(K) → Create(K)           → K survives (resurrected)
    Create(K) → Update(K) → Update(K)           → K survives (latest)

4.11 CORRUPTION HANDLING

Invalid Magic Log truncated at first invalid byte; recovery stops
Hash Chain Broken Log truncated; possible tampering detected
CRC Mismatch (Replay) Log truncated at mismatch
CRC Mismatch (Compaction) Record skipped, compaction continues
Incomplete Record Log truncated at incomplete boundary

5. CORE OPERATIONS

5.1 CONNECTION ESTABLISHMENT

  1. Client initiates WebSocket upgrade request to port 8080
  2. Server accepts connection, assigns to worker thread
  3. Client sends AUTH frame with JWT token
  4. Server validates token, returns AUTH_ACK
  5. Connection ready for subscription

5.2 MESSAGE TRANSMISSION

  1. Client sends MESSAGE frame with room ID and payload
  2. Server routes to room's assigned thread
  3. Thread queues message to all subscribers in room
  4. Subscribers receive message in real-time
  5. Message discarded after delivery (ephemeral)

5.3 ROOM SUBSCRIPTION

  1. Client sends SUBSCRIBE frame with room ID
  2. Server adds connection to room's subscriber list
  3. Client begins receiving messages from room
  4. To unsubscribe, send UNSUBSCRIBE frame

8. OPERATIONAL PROCEDURES

8.1 STARTUP SEQUENCE

  1. Verify kernel version: uname -r (minimum 5.1)
  2. Verify io_uring support: cat /proc/sys/kernel/io_uring_max_files
  3. Build server: odin build . -out:server
  4. Execute: ./server
  5. Wait for "NRC-300 READY" message on stdout
  6. Verify metrics endpoint responds

8.2 SHUTDOWN PROCEDURE

  1. Send SIGINT to process (Ctrl+C)
  2. Server closes new connections
  3. Waits 500ms for graceful client shutdown
  4. Persists outstanding task state
  5. Exit with code 0

8.3 HEALTH MONITORING

Real-time metrics visible in NRC-300 UI:

  • Active connections per thread
  • Message throughput (msgs/sec)
  • Memory usage (resident set size)
  • CPU utilization per core
  • Latency percentiles (p50, p95, p99)

9. TROUBLESHOOTING

9.1 CONNECTION FAILURES

SYMPTOM: Clients unable to connect to server

  1. Verify server is running: ps aux | grep server
  2. Check port binding: netstat -tlnp | grep 8080
  3. Verify firewall rules: sudo iptables -L
  4. Check system logs: journalctl -u nrc

9.2 HIGH LATENCY

SYMPTOM: Messages taking >100ms to deliver

  1. Monitor thread load: check metrics in NRC-300
  2. Verify io_uring rings are not saturated
  3. Check CPU thermal throttling
  4. Reduce connection density or scale horizontally

9.3 MEMORY LEAKS

SYMPTOM: Memory usage grows unbounded

  1. Build with debug: odin build . -out:server -debug
  2. Run memory checker: output shows leak summary on shutdown
  3. Check for unclosed message buffers
  4. Verify all subscriptions cleaned up properly
