BUTTONS

.btn

RULE Jede gewöhnliche Aktion verwendet .btn aus der zentralen Button-Familie. Modifier ändern nur die Semantik: eine Primäraktion pro Bereich, Secondary für nachrangige Aktionen, Ghost für sichere Ausstiege und Danger nur für destruktive oder abbrechende Aktionen. Die Rolle entscheidet über den Modifier: Anlegen einer neuen Entität trägt die eine Primäraktion des Registers (header-create-action, zum Beispiel + TASK, + SLICE, + NOTE); Zuordnen einer bestehenden Entität ist eine gewöhnliche Aktion (.btn, zum Beispiel + ASSIGN TASK, + ASSIGN NOTE, + LINK, LINK COMPANY, + LINK EXISTING) — ebenso das Lösen einer Zuordnung, weil beide Entitäten bestehen bleiben (UNASSIGN, UNLINK), und das reversible Schließen eines Slice (CLOSE SLICE, REOPEN SLICE); Danger bleibt Datenverlust und Abbrüchen vorbehalten (DELETE, STOP). Gefahrenfarben verwenden semantisches Rot, unabhängig von der dekorativen Theme-Palette. WIEDERHOLUNG Eine Zeilen-Aktion (btn--row) ist die eine Ausnahme von der Fläche: sie steht einmal pro Tabellenzeile, wo ein Kasten pro Zeile zur Textur wird und der Datenspalte den Platz nimmt. Sie bleibt als Beschriftung in --text-dim sichtbar — nicht versteckt — und holt sich den Akzent erst bei eigenem Hover oder Tastaturfokus; die Zeile selbst behält ihren eigenen Hover-Zustand aus dem Listen-Vertrag; eine destruktive Zeilen-Aktion trägt zusätzlich btn--danger und zeigt ihre Bedeutung im Hover statt als roten Kasten in jeder Zeile. Sie erscheint in den Slice-Member-Tabellen, der Firmen-Tabelle eines Kontakts, den Anhang- und Link-Zeilen und in der Chat-Zeile. Feature-CSS darf Position und Größe, aber nicht Rahmen, Fläche, Schatten oder Interaktionszustände neu definieren.

SEGMENTED TABS

.tab-group .nav-tab

RULE Alle horizontalen Tabs (DEPTH, Reminder-Filter, DETAIL/COMMENTS und NOTE/TASK) verwenden denselben Produktionsstil: Die Gruppe füllt das Band, das sie hält — Segmente in voller Bandhöhe, ohne eigenes Zellenlabel im Inspector. Die Segmente stoßen ohne Abstand aneinander und ziehen eine gemeinsame 1px-Grundlinie unter der Gruppe; das gewählte Segment ersetzt sie durch eine 3px-Akzentlinie. Eine Zahl steht in einem eigenen .tab-count-Slot mit fester Mindestbreite, damit eine zweite Ziffer in reservierten Platz wächst statt die Gruppe und die folgenden Bedienelemente zu verschieben. Keine Segmentrahmen, transparente Grundfläche, gemeinsame Typografie, identischer Hover- (Fläche ohne Rahmen) und Fokuszustand (2px innen). Container dürfen nur die Breite verteilen. Die vertikale Sidebar-Navigation ist eine eigene Komponente.

CONTRACT Registers use a uniform 20px metadata band with 10px text above compact, flat controls. Filter and instrument registers apply this automatically; all chat views use .metadata-header-register. Chat keyboard hints and readouts remain in this compact band, with inline statistics. Output headers remain one full-height row; inspector identity rows use the same 20px band above mode/action rows. Creation-capable workspaces expose one explicit, right-aligned, filled header-create-action; chat and system output do not invent redundant creation operations. ACTIONS Ordinary operations use one-line verbs without synthetic OP numbers. WIDTH QUERY is first, presents its label beside a bounded input, and takes the flexible remaining width. Desktop dropdowns read as one-line LABEL: VALUE registers in every filter register, and every control keeps its own bounded surface: search its field, dropdowns their trigger, toggles and operations their button. Register cells draw no divider between one another, so the header never reads as a table of columns. Dropdowns have bounded widths; toggles, mode groups and actions fit their labels. GROUPING The task register's GROUP toggle swaps the flat-list parameter cells for the slice filters in the same row, and the cells stay direct children of the scrolling control row so one register contract covers both: QUERY narrows by slice name, OWNER by whose work stream a row is (ALL / MY SLICES / UNASSIGNED / one owner), and INCLUDE CLOSED decides whether closed slices are listed. Every slice filter is the server's, the way the task query filters tasks: the page that arrives is already the filtered one, and the register asks for the next page as the reader reaches the end of the drawn rows. A register that has drawn part of its listing reads N / M SLICES — like the task table's N / M RESULTS — and its matching count alone once all of it is drawn, and a filter that matches nothing says so instead of reading as an empty workspace. Without a search field, spare space separates left-aligned modes/context from right-aligned operations. Inspector BACK stays beside VIEW, with one flexible gap after the tabs. Desktop controls remain a single row and scroll horizontally rather than wrapping. Mobile task filters expand into a bounded, vertically scrolling two-column form: query plus creation remain available when collapsed; expanded filters use 44px controls, the combined FLAGS select, and plain action labels without OP/MODE annotations.

PAGE LOADER

<nrc-page-loader>

CONTRACT Light DOM, shared buttons and status. setState({ hasMore, loading, error, disabled, active, root, label }) updates the paging UI. The component requests another page through nrc:load-more when the button approaches the scroll boundary or is activated. The owner immediately publishes loading state and later success or error. Errors stop automatic loading and expose RETRY; exhausted lists hide the control. Hidden, inactive and disconnected loaders do not request pages. Disconnecting releases the observer. Requests, cursors, filters, stale-response guards, rows and virtual scrolling remain with the owner. The examples display fixed states without a data source.

ROW STATES Tasks, notes, reminders, customers, contacts, slices, slice members and system-log rows share the state rules in css/main.css. Selection uses a tinted background and a 3px left accent; hover never replaces selection. Selection, pointer hover and keyboard focus all show the same 1px inset outline around the whole row, including when its title button has focus. Attention and customer activity rows share hover and focus but have no persistent selection.

ROW DIVIDERS Entity registers share the divider rules in css/main.css: 1px in --border-list, below rows or above contacts and slice members. Task rows own the divider in both table and compact grid layouts. Entity and responsive styles only set geometry; do not redeclare divider appearance there. Headers retain their stronger rules, file sections omit the final divider, and virtual spacers remain borderless. System-log rows remain unruled.

LONG LISTS Task and Note lists above 100 loaded results mount only the viewport plus overscan. Arrow navigation follows the complete filtered order, including offscreen rows. Note pagination remains at the loaded boundary. Measured row heights support wrapping and column resizing; focused controls and a dragged Task remain mounted until focus or drag ends. Task drag near the viewport edge auto-scrolls. The row appearance and selection contract below also apply to virtual rows.

WORKSPACE DATA Rooms organize chats only. Tasks, notes, customers, files and graph links use one workspace scope. Changing chat rooms preserves entity selection, edits, filters and loaded pages; opening an entity link preserves the active chat. Entity links need no room. Task and note activity appears in SYSTEM LOG, not a synthetic chat room.

TASK QUERIES Filters and sorting apply server-side before pagination. OPEN is the default and excludes DONE; ALL includes every task status. The result counter shows loaded / matching results, and scrolling near the loaded boundary extends the same ordered query automatically. Filter and sort changes restart paging; chat room changes do not. Live task changes refresh the query. QUERY FAILED exposes failures without implying an empty result. Text search retains its separate top-100 ranked results. Project choices include unloaded tasks.

STATUS IN PLACE The status a task register draws is the control that changes it: the token reads exactly as it always has, and pressing it opens the statuses in place, so a task is re-statused without opening it and without entering edit mode. The menu is the shared picker the detail panel's STATUS field opens, built when it is opened rather than with the row, so a register of a thousand tasks carries a thousand tokens and no dropdowns. The write is the board's own move rather than a second mutation path, and the register asks for the end of the column it enters instead of naming a position: a register holds one page of a column, so the server folds the position and answers with it, exactly as it derives completed_at and completed_by from the transition for a drag. A redraw takes the menu whose token it rebuilds with it, and a table redrawn elsewhere leaves it alone; an outside press and Escape close it, and Escape gives the token its focus back. The row carries the focus outline, like every other opener inside a row. The flat register and a slice's member table draw the same token and the same menu, so one task reads its status the same in both.

SLICE REGISTER

WORK IN PROGRESS

CONTRACT A slice is an explicit work stream: an asset of type 11, created by name and unique within the conversation, whose members are the tasks, notes and files linked to it with a member-of edge. Membership is an edge, so a slice spans projects and one task can belong to several slices; a project label says which repository something belongs to, a slice says which work stream it moves. The server folds every counter from the membership edges and the client derives nothing, so the register, the record and the CLI read one definition of membership and cannot disagree. Work without a slice is counted, not invented into a bucket: the register head reports how many tasks carry no slice, and those tasks are ordinary work in the flat list. The register is the distance view: one row per slice, carrying the counters the listing sends as a bar of status shares. Member identity and member order are not on the wire for a register, so the register draws neither: its bar is the share each status holds, and under it the blocked share drawn against the whole slice, because a count cannot name the member it belongs to. A bar is always the whole slice, so a nearly-done slice and a mostly-backlog slice are comparable across rows, while the member count stays a number in the row head. The record, which holds the members, is the one surface that draws them: one mark each in creation order, with the blocked members breaking out of the band where they sit, and it draws the counters bar until the members land. Counters turn danger-colored above six open members, and movement turns muted after a week. Status marks use the --status-* ramp, never the --accent-* aliases, because several themes remap the accent names onto a decorative palette and a shape has no words to carry the meaning. Closure is an act by the owner, not a consequence of the last member reaching Done: a closed slice leaves the register until the CLOSED filter is switched on, and reopening it is the same act reversed. The first token of every row is whose work stream it is, because that is what the register's owner filter narrows by — ALL, MY SLICES, UNASSIGNED or one owner, beside a query that narrows by the name a slice is addressed by. The filters are the server's, the way the task query filters tasks, so a filtered listing is complete rather than a narrowing of the window that happened to be loaded; MY SLICES resolves into the reader's own name, exactly as MY TASKS resolves the assignee. The listing is paged for the same reason: a workspace piles up work streams, closed ones included, so the register draws a page and asks for the next one as the reader reaches the end of the drawn rows — by scrolling, or by walking past the last row with the arrow keys. The head reads N / M SLICES while part of the listing is drawn and M SLICES once all of it is, and the open count is folded from the drawn rows, like the task register's alerts. A filter that matches nothing says NO SLICES MATCH THE FILTER instead of reading as an empty workspace. The open record follows the listing: a page that does not carry it opens the first row drawn, unless the reader has unsaved work in that record, which stays where it is. A slice that was just created drops the filter, because it carries no owner yet and must not be hidden by the filter that was set before it. Creating, assigning and unassigning are the writes; a slice name is the identity the register, the record and the CLI address it by, so two slices cannot share one. Deleting is the one write that cannot be undone — closure has REOPEN and membership has assign — so it is the only guarded action in the record: the control asks before it sends and names the memberships it releases, and nrc slice delete refuses a slice that carries members, an owner or an outcome until the caller passes --force. The members are never part of a delete: their records stay and the register counts them as work without a slice again. The record refreshes in place: a background refresh keeps the rows that are already on screen and says so when the server cannot be reached, because a list that is replaced under the reader's pointer takes the click that is on its way to it. Every task a member table draws carries the register's status token, and that token is the control that changes the status in place: a member is re-statused without opening it, and the write is the move the flat register writes, so the two tables cannot disagree about how a status changes. A member row is the target rather than its title alone: the row carries the reference, the title inside it is the control the keyboard reaches, and the arrow keys walk the register and every member table the way they walk the other lists in the client. The row that moves is the row that opens: an arrow in the register changes the slice on screen, and an arrow in a member table opens the adjacent member in the inspector. A member table is walked from the member the reader last opened or focused, because a click on a row leaves focus on the record itself.
