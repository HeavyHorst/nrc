BUTTONS

.btn

RULE Jede gewöhnliche Aktion verwendet .btn aus der zentralen Button-Familie. Modifier ändern nur die Semantik: eine Primäraktion pro Bereich, Secondary für nachrangige Aktionen, Ghost für sichere Ausstiege und Danger nur für destruktive oder abbrechende Aktionen. Die Rolle entscheidet über den Modifier: Anlegen einer neuen Entität trägt die eine Primäraktion des Registers (header-create-action, zum Beispiel + TASK, + SLICE, + NOTE); Zuordnen einer bestehenden Entität ist eine gewöhnliche Aktion (.btn, zum Beispiel + ASSIGN TASK, + ASSIGN NOTE, + LINK, LINK COMPANY, + LINK EXISTING) — ebenso das Lösen einer Zuordnung, weil beide Entitäten bestehen bleiben (UNASSIGN, UNLINK), und das reversible Schließen eines Slice (CLOSE SLICE, REOPEN SLICE); Danger bleibt Datenverlust und Abbrüchen vorbehalten (DELETE, STOP). Gefahrenfarben verwenden semantisches Rot, unabhängig von der dekorativen Theme-Palette. WIEDERHOLUNG Eine Zeilen-Aktion (btn--row) ist die eine Ausnahme von der Fläche: sie steht einmal pro Tabellenzeile, wo ein Kasten pro Zeile zur Textur wird und der Datenspalte den Platz nimmt. Sie bleibt als Beschriftung in --text-dim sichtbar — nicht versteckt — und holt sich den Akzent erst bei eigenem Hover oder Tastaturfokus; die Zeile selbst behält ihren eigenen Hover-Zustand aus dem Listen-Vertrag; eine destruktive Zeilen-Aktion trägt zusätzlich btn--danger und zeigt ihre Bedeutung im Hover statt als roten Kasten in jeder Zeile. Sie erscheint in den Slice-Member-Tabellen, der Firmen-Tabelle eines Kontakts, den Anhang- und Link-Zeilen und in der Chat-Zeile. Feature-CSS darf Position und Größe, aber nicht Rahmen, Fläche, Schatten oder Interaktionszustände neu definieren.

LOADING FEEDBACK Read indicators in Overview, Calendar, Slices, Tasks, Notes, Customers and page loaders appear only after 150 ms of continuous loading. Fast reads replace content directly. Existing content is retained where available. Busy semantics and action guards apply immediately; errors, offline notices and incomplete-data warnings are never delayed. Finishing or cancelling a read cancels its pending indicator.

CONTRACT Light DOM, shared buttons and status. setState({ hasMore, loading, error, disabled, active, root, label }) updates the paging UI. The component requests another page through nrc:load-more when the button approaches the scroll boundary or is activated. The owner immediately publishes loading state and later success or error. Errors stop automatic loading and expose RETRY; exhausted lists hide the control. Hidden, inactive and disconnected loaders do not request pages. Disconnecting releases the observer. Requests, cursors, filters, stale-response guards, rows and virtual scrolling remain with the owner. The examples display fixed states without a data source.

ROW STATES Tasks, notes, reminders, customers, contacts, slices, slice members and system-log rows share the state rules in css/main.css. Selection uses a tinted background and a 3px left accent; hover never replaces selection. Selection, pointer hover and keyboard focus all show the same 1px inset outline around the whole row, including when its title button has focus. Attention and customer activity rows share hover and focus but have no persistent selection.

ROW DIVIDERS Entity registers share the divider rules in css/main.css: 1px in --border-list, below rows or above contacts and slice members. Task rows own the divider in both table and compact grid layouts. Entity and responsive styles only set geometry; do not redeclare divider appearance there. Headers retain their stronger rules, file sections omit the final divider, and virtual spacers remain borderless. System-log rows remain unruled.

LONG LISTS Task and Note lists above 100 loaded results mount only the viewport plus overscan. Arrow navigation follows the complete filtered order, including offscreen rows. Note pagination remains at the loaded boundary. Measured row heights support wrapping and column resizing; focused controls and a dragged Task remain mounted until focus or drag ends. Task drag near the viewport edge auto-scrolls. The row appearance and selection contract below also apply to virtual rows.

CONTRACT A slice is an explicit work stream: an asset of type 11, identified by its stable numeric asset ID, whose members are the tasks, notes and files linked to it with a member-of edge. Membership is an edge, so a slice spans projects and one task can belong to several slices; a project label says which repository something belongs to, a slice says which work stream it moves. The server folds every counter from the membership edges and the client derives nothing, so the register, the record and the CLI read one definition of membership and cannot disagree. Work without a slice is counted, not invented into a bucket: the register head reports how many tasks carry no slice, and those tasks are ordinary work in the flat list. The register is the distance view: one row per slice, carrying the counters the listing sends as a bar of status shares. Member identity and member order are not on the wire for a register, so the register draws neither: its bar is the share each task status holds, with the count inside each segment. The order is BACKLOG, TODO, IN PROGRESS, DONE. Zero counts draw no segment; tiny segments retain their true proportion and hide the number rather than clipping it or widening the share. The complete counts remain in the bar's accessible label and tooltip. Blocked overlaps the statuses, so its red text count stays below the bar, not in an additional segment. The name and total member count form the row head; the owner shares the compact metadata row below the bar with blocked count, movement and closure rather than occupying a line of its own. Row padding, gaps and bar height are compact without shrinking the text. Notes and files count toward MEM but not toward the task bar, and their own counts stay in the detail. A bar is always all task members, so a nearly-done slice and a mostly-backlog slice are comparable across rows. The record fills the available pane with two aligned summaries: facts, status bar and percentage swatches on the left, and a separate blocked bar on the right behind a vertical rule. Counts stay inside the status bar; percentages appear only in its color-swatch legend. Blocked names its overlap with task statuses and uses all tasks as its denominator. On narrow record panes the two summaries stack. No tasks are omitted, and no creation order is implied. Detail counters turn danger-colored above six open members, and movement turns muted after a week. Status segments use the --status-* ramp, never the --accent-* aliases, because several themes remap the accent names onto a decorative palette. Closure is an act by the owner, not a consequence of the last member reaching Done: a closed slice leaves the register until the CLOSED filter is switched on, and reopening it is the same act reversed. The owner filter narrows by whose work stream it is — ALL, MY SLICES, UNASSIGNED or one owner, beside a query that searches its display name. The filters are the server's, the way the task query filters tasks, so a filtered listing is complete rather than a narrowing of the window that happened to be loaded; MY SLICES resolves into the reader's own name, exactly as MY TASKS resolves the assignee. The listing is paged for the same reason: a workspace piles up work streams, closed ones included, so the register draws a page and asks for the next one as the reader reaches the end of the drawn rows — by scrolling, or by walking past the last row with the arrow keys. The head reads N / M SLICES while part of the listing is drawn and M SLICES once all of it is, and the open count is folded from the drawn rows, like the task register's alerts. A filter that matches nothing says NO SLICES MATCH THE FILTER instead of reading as an empty workspace. An explicit filter change selects the first matching row unless the open record has unsaved work. Background refreshes retain an explicitly selected ID even outside the current page or filter. A slice that was just created drops the filter, because it carries no owner yet and must not be hidden by the filter that was set before it. The register, record, links and CLI address existing slices by ID; names are mutable display labels and may repeat. Creating still takes a name; nrc slice update <id> --name <label> changes it without changing memberships. Deleting is the one write that cannot be undone — closure has REOPEN and membership has assign — so it is the only guarded action in the record: the control asks before it sends and names the memberships it releases, and nrc slice delete refuses a slice that carries members, an owner or an outcome until the caller passes --force. The members are never part of a delete: their records stay and the register counts them as work without a slice again. The record refreshes in place: a background refresh keeps the rows that are already on screen and says so when the server cannot be reached, because a list that is replaced under the reader's pointer takes the click that is on its way to it. Every task a member table draws carries the register's status token, and that token is the control that changes the status in place: a member is re-statused without opening it, and the write is the move the flat register writes, so the two tables cannot disagree about how a status changes. A member row is the target rather than its title alone: the row carries the reference, the title inside it is the control the keyboard reaches, and the arrow keys walk the register and every member table the way they walk the other lists in the client. The row that moves is the row that opens: an arrow in the register changes the slice on screen, and an arrow in a member table opens the adjacent member in the inspector. A member table is walked from the member the reader last opened or focused, because a click on a row leaves focus on the record itself.
